# Потребление электричества в доме: анализ, SQL, прогноз и дашборд

Итоговый мини-проект по курсу **Programming for Data Analysis and Database** (тема 11, Household Energy Consumption, кластер 2).

## Данные

[Individual Household Electric Power Consumption](https://archive.ics.uci.edu/dataset/235/individual+household+electric+power+consumption), UCI.
Один дом во Франции, замеры каждую минуту с 16.12.2006 по 26.11.2010: **2 075 259 строк**, около 133 МБ.
Мощность (кВт), напряжение (В), сила тока (А) и три счётчика по зонам дома (Вт·ч): кухня, прачечная, водонагреватель и кондиционер.
Пропуски (в файле они записаны как `?`): 25 979 минут, 1,25 % данных.

Файл данных в репозиторий не входит. Скачай архив по ссылке выше, распакуй и положи
`household_power_consumption.txt` в папку `data/`.

## Запуск

```bash
pip install -r requirements.txt
python main.py all          # все шаги подряд (около 40 секунд)
streamlit run app.py        # дашборд
```

Без аргументов `python main.py` открывает консольное меню. Шаги можно запускать по одному:
`python main.py load | db | analyze | plots | forecast`.

Работает в обычной консоли, VS Code, PyCharm и Google Colab (в Colab загрузи файл в `data/` и запускай `!python main.py all`).

## Что сделано

**1. Данные и память.** Файл читается по частям (`chunksize=200 000`), даты собираются в `timestamp`, `?` превращается в пропуск, `float64` переводится в `float32`.
Память DataFrame: 338,3 МБ без оптимизации, 71,2 МБ после (минус 78,9 %). Чистые данные сохраняются в Parquet
(если не установлен `pyarrow`, то в `csv.gz`). Сравнение CSV и Parquet по размеру и времени чтения записывается в `results/load_report.json`.

**2. Аудит качества.** Пропуски по столбцам, дубликаты меток времени (0), пропущенные минуты в ряду (0, строки есть, значения пустые),
отрицательные значения (0). Часы без единого измерения не попадают в базу и находятся запросом `q09` через `LAG`.

**3. SQLite и SQL.** Схема в третьей нормальной форме: `dim_date`, `dim_meter`, `fact_hourly`, `fact_hourly_meter` (ER-диаграмма: `results/erd.png`).
Ограничения: `PRIMARY KEY`, `FOREIGN KEY` (`RESTRICT` и `CASCADE`), `CHECK`, `UNIQUE`, `NOT NULL`. 10 запросов:
`JOIN`, `GROUP BY` и `HAVING`, подзапрос, `CTE`, оконные функции `AVG OVER`, `LAG`, `RANK`, `SUM OVER`, `CASE`.
Результаты загружаются в Pandas. Расчёт «кВт·ч по месяцам» сделан в SQL и в Pandas: результаты совпадают.

**4. EDA и временные ряды.** Описательная статистика, выбросы по правилу 1,5·IQR, ресемплинг час, день, неделя, месяц, скользящие средние за 7 и 30 дней,
сезонная декомпозиция (тренд, сезонность, остаток), корреляции.

**5. Графики.** `figures/01_daily_trend.png`, `02_hourly_profile.png`, `03_decomposition.png`, `04_correlation.png`,
интерактивный `05_interactive_meters.html` (Plotly, ползунок диапазона дат). Дополнительно `06_forecast_test.png`.

**6. Прогноз и сравнение методов.** Задача: потребление на следующий день. Разбиение по времени: тест это последние 365 дней, без перемешивания.
Метрика MAE (кВт·ч в сутки), также RMSE, время и память.

| Метод | MAE | RMSE |
|---|---|---|
| naive, как вчера (baseline) | 5,17 | 7,13 |
| seasonal naive, как неделю назад | 5,98 | 7,98 |
| скользящее среднее 7 дней | 4,34 | 5,90 |
| линейная регрессия | **4,30** | 5,90 |

Линейная регрессия и скользящее среднее лучше baseline примерно на 16–17 %. Разница между ними мала, поэтому
скользящее среднее можно считать почти равным по качеству и гораздо более простым.

**7. Дашборд.** Фильтры: период, шаг агрегации, показатель, сезон, тип дня. Вкладки: обзор, суточный профиль, счётчики, прогноз, SQL-запросы.

## Ограничения

- Прогноз строится на одном доме и одном годе теста, обобщать результат на другие дома нельзя.
- 19 пропущенных суток при прогнозе заполнены линейной интерполяцией. Метрики считаются только по реальным дням.
- В августе 2008 года в данных заметный провал потребления (вероятно, отпуск). Это обычное поведение, а не ошибка данных.
- Расход за период в дашборде считается по имеющимся часам, поэтому при пропусках немного занижен.
