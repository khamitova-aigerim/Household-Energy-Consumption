## Данные

Использован набор данных [Individual Household Electric Power Consumption](https://archive.ics.uci.edu/dataset/235/individual+household+electric+power+consumption) (UCI Machine Learning Repository).
Данные относятся к одному дому во Франции: измерения выполнялись каждую минуту с 16.12.2006 по 26.11.2010, всего **2 075 259 строк** (около 133 МБ).
Набор содержит мощность (кВт), напряжение (В), силу тока (А) и показания трёх счётчиков по зонам дома (Вт·ч): кухня, прачечная, водонагреватель и кондиционер.
Пропуски в исходном файле обозначены символом `?`: 25 979 минут, или 1,25 % данных.

Файл данных в репозиторий не включён из-за большого объёма. Для запуска проекта необходимо загрузить архив по ссылке выше, распаковать его и поместить файл
`household_power_consumption.txt` в папку `data/`.

## Запуск

```bash
pip install -r requirements.txt
python main.py all          # выполнение всех шагов подряд (около 40 секунд)
streamlit run app.py        # запуск дашборда
```

При запуске `python main.py` без аргументов открывается консольное меню. Шаги можно выполнять по отдельности:
`python main.py load | db | analyze | plots | forecast`.

Проект работает в консоли, VS Code, PyCharm и Google Colab (в Colab файл данных необходимо поместить в `data/` и выполнить `!python main.py all`).

## Что выполнено

**1. Загрузка данных и использование памяти.** Файл читается по частям (`chunksize=200 000`), дата и время объединяются в `timestamp`, символ `?` заменяется на пропуск, тип `float64` приводится к `float32`.
Объём памяти DataFrame: 176,0 МБ при стандартном чтении и 71,2 МБ после оптимизации (сокращение на 59,5 %). Очищенные данные сохраняются в Parquet
(при отсутствии библиотеки `pyarrow` используется `csv.gz`). Сравнение форматов: CSV занимает 109,3 МБ и читается за 1,22 с, Parquet занимает 22,0 МБ и читается за 0,13 с.
Результаты сравнения записываются в `results/load_report.json`.

**2. Проверка качества данных.** Выполнена проверка пропусков по столбцам, дубликатов меток времени (0), пропущенных минут во временном ряду (0: строки присутствуют, значения пустые)
и отрицательных значений (0). Часы без единого измерения не попадают в базу данных и выявляются запросом `q09` с помощью `LAG`.

**3. SQLite и SQL.** Схема приведена к третьей нормальной форме: `dim_date`, `dim_meter`, `fact_hourly`, `fact_hourly_meter` (ER-диаграмма: `results/erd.png`).
Использованы ограничения `PRIMARY KEY`, `FOREIGN KEY` (`RESTRICT` и `CASCADE`), `CHECK`, `UNIQUE`, `NOT NULL`. Составлено 10 запросов:
`JOIN`, `GROUP BY` и `HAVING`, подзапрос, `CTE`, оконные функции `AVG OVER`, `LAG`, `RANK`, `SUM OVER`, `CASE`.
Результаты загружаются в Pandas. Расчёт «кВт·ч по месяцам» выполнен средствами SQL и Pandas, результаты совпадают.

**4. EDA и временные ряды.** Выполнены описательная статистика, поиск выбросов по правилу 1,5·IQR, ресемплинг (час, день, неделя, месяц), скользящие средние за 7 и 30 дней,
сезонная декомпозиция (тренд, сезонность, остаток) и корреляционный анализ.

**5. Визуализации.** `figures/01_daily_trend.png`, `02_hourly_profile.png`, `03_decomposition.png`, `04_correlation.png`,
интерактивный график `05_interactive_meters.html` (Plotly, ползунок диапазона дат). Дополнительно построен `06_forecast_test.png`.

**6. Прогноз и сравнение методов.** Задача: прогноз потребления на следующий день. Выборка разделена по времени: тестовая часть составляет последние 365 дней, данные не перемешивались.
Метрика качества: MAE (кВт·ч в сутки); дополнительно рассчитаны RMSE, время выполнения и объём памяти.

| Метод | MAE | RMSE |
|---|---|---|
| naive, значение предыдущего дня (baseline) | 5,17 | 7,13 |
| seasonal naive, значение недельной давности | 5,98 | 7,98 |
| скользящее среднее за 7 дней | 4,34 | 5,90 |
| линейная регрессия | **4,30** | 5,90 |

Линейная регрессия и скользящее среднее точнее базовой модели примерно на 16–17 %. Разница между ними невелика, поэтому
скользящее среднее можно считать сопоставимым по качеству и существенно более простым методом.

**7. Дашборд.** Фильтры: период, шаг агрегации, показатель, сезон, тип дня. Вкладки: обзор, суточный профиль, счётчики, прогноз, SQL-запросы.

## Ограничения

- Прогноз построен на данных одного дома и одного тестового года, поэтому результаты нельзя переносить на другие домохозяйства.
- 19 пропущенных суток при подготовке прогноза заполнены линейной интерполяцией; метрики рассчитываются только по фактическим дням.
- В августе 2008 года в данных наблюдается заметное снижение потребления; возможная причина — отсутствие жильцов в период отпуска. В данных причина не указана, это предположение.
- Расход за период в дашборде рассчитывается по имеющимся часам, поэтому при наличии пропусков значение несколько занижено.
